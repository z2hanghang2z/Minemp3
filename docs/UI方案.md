# UI 方案设计 · 手持 MP3 播放器

> 版本 v1 · 2026-11-12
> 范围变更：**不做歌词**（P3 整段砍掉），UI 走原版像素风，主界面只留核心歌曲信息

---

## 一、设计原则

1. **像一件物品，不像一个网页** —— 所有控件都要有物理感：凹槽、凸起按键、按下位移 1px
2. **一屏只讲一件事** —— 主界面就是"现在在放什么"，不做信息堆叠
3. **零自定义贴图以外的装饰** —— 边框、按钮全部用 1px 明暗边做出立体感，不用渐变、不用圆角、不用阴影
4. **二级功能折叠** —— 搜索、歌单不占主屏，收进页签或独立入口

---

## 二、核心信息取舍

| 信息 | 去留 | 理由 |
|---|---|---|
| 专辑封面 | **必留** | 唯一能一眼认出"在放什么"的视觉锚点 |
| 歌名 | **必留** | 核心 |
| 歌手 | **必留** | 核心 |
| 进度条 + 已播/总时长 | **必留** | 没有它就不像播放器 |
| 播放/暂停状态 | **必留** | 按钮形态本身就是状态 |
| 音量 | 可选 | 塞进设置页，主屏只留图标 |
| 循环 / 随机模式 | 可选 | 一个小图标即可 |
| 音质标签（标准/较高/极高） | 可选 | 一行小字，放设置页 |
| 歌词 | **删** | 已明确不做 |
| 频谱动画 | **删** | 原版像素风里很违和，且耗性能 |
| 歌单/搜索 | 折叠 | 收进页签，不占主屏 |

## 三、四套方案

### 方案 A · 口袋机（Pocket Player）

**一句话**：iPod nano 式的竖屏机，所有信息一屏装完。

| 项 | 内容 |
|---|---|
| 界面尺寸 | 176×166 标准 MC 容器，纵向布局 |
| 主屏构成 | 48×48 封面 + 歌名 + 歌手 / 横向进度条 + 双时间 / 音量与循环小图标 / 十字方向键 + 中央播放键 |
| 交互 | 鼠标点按钮；方向键 ↑↓ 切歌、←→ 快退快进、Enter 播放暂停 |
| 二级页 | 底部 4 个页签：播放 / 搜索 / 歌单 / 设置，像素图标切换 |
| 技术成本 | **低**：1 个 Screen + 3 个二级页，无动画 |
| 优点 | 信息最全、手感最正、开发最快、扩展性最好 |
| 缺点 | 视觉记忆点一般，跟"手持设备"的关联靠物品模型而非界面 |

### 方案 B · 卡带机（Cassette）

**一句话**：界面就是一个卡带仓，走带量即进度。

| 项 | 内容 |
|---|---|
| 界面尺寸 | 176×166，横向布局 |
| 主屏构成 | 双卷轴磁带窗（播放时旋转）+ 磁带标签条 / LCD 单行信息（歌名 + 剩余时间 + 细进度线）/ 一排机械按键（⏮ ▶ ⏭ ⏹） |
| 交互 | 4 个机械按键，按下有 1px 位移；无页签，搜索/歌单靠快捷键唤出 |
| 视觉细节 | 卷轴 3 帧循环动画；播放中磁带呈深色，暂停时变灰 |
| 技术成本 | **中**：手绘 3 帧卷轴 + 磁带路径 + 按键动效 |
| 优点 | 拟物感最强、辨识度最高、截图传播性强 |
| 缺点 | 信息密度最低（只剩歌名和剩余时间）、扩展性差、动画占开发时间 |

### 方案 C · 无界面 HUD 条（Glanceable）

**一句话**：平时不打开界面，右下角一条像素信息条。

| 项 | 内容 |
|---|---|
| 界面尺寸 | HUD 条 128×26，贴屏幕右下 |
| 构成 | 16×16 像素封面 + "歌名 - 歌手" + 底部 2px 进度细线 |
| 交互 | 右键 = 播放/暂停；Shift+右键 = 打开完整界面；P 暂停、`[` `]` 切歌、滚轮音量 |
| 视觉细节 | 半透明黑底 + 原版字体；3 秒无操作淡出，鼠标移到区域重新浮现 |
| 技术成本 | **低**：1 个 HUD 渲染器 + 1 个快捷键注册 |
| 优点 | 完全不打断游戏、最贴近"边玩边听"、工作量最小 |
| 缺点 | 不能拖进度、不能选歌、信息极其有限，必须配一个完整界面兜底 |

### 方案 D · 手持 / 落地双形态（Boom Box）

**一句话**：拿在手上是随身听，放到地上变成收音机。

| 项 | 内容 |
|---|---|
| 界面尺寸 | 手持时走 HUD 条；方块形态打开 176×166 面板 |
| 形态切换 | 右键空气 = 打开界面；右键方块顶面 = 放置；潜行右键 = 收回 |
| 方块表现 | 正面喇叭格栅 + 顶部小屏（显示歌名首字）+ 播放时格栅 2 帧震动动画 |
| 空间音效 | 手持时声源绑玩家；落地后声源绑方块坐标，走远衰减、隔墙低通变闷 |
| 技术成本 | **高**：方块 + BlockEntity + 渲染 + 状态同步 + 音源位置切换 |
| 优点 | **唯一能体现空间音效的形态**，也是和市面所有模组拉开差距的点 |
| 缺点 | 工作量最大，且要处理多人服务器下的状态同步 |

## 五、推荐：A + C + D 组合

不是四选一，最优解是**三层叠加**：

```
主界面（A 口袋机布局）      ← 打开就有全部信息，成本最低
        +
手持提示（C HUD 条）        ← 不打开界面也能看见在放什么
        +
落地形态（D 方块）          ← 空间音效的载体，差异化核心
```

理由：

- **A 当主界面**：176×166 是原版容器的标准尺寸，布局有成熟参考，一天能搭完骨架
- **C 当常态**：玩家 90% 时间不会开界面，HUD 条负责"我知道在放什么"，且成本几乎为零
- **D 当亮点**：这是唯一能让"空间感"这个卖点落地的形态，也是宣传素材

B 的卷轴动画可以做成**物品皮肤/彩蛋**——比如播放器用"卡带"材质时主界面换成 B 的样式，但那是 v2 的事。

## 六、物品视觉规范

手持模型（第一人称）必须做到三件事，否则"手持 MP3"的感觉立不住：

1. **模型比例**：12×12×3 像素的扁平设备，比地图略小，握在手里像块砖
2. **屏幕 2 帧动画**：播放时屏幕上有一格一格爬动的进度条（2 帧循环，每 0.5 秒切一次）；暂停时定格
3. **右键反馈**：打开界面时物品有个 1 像素的下沉，配合一声轻微的"咔哒"音效

---

## 七、封面像素化规范

网络封面是高清 JPEG，直接贴进 176×166 的像素界面会非常割裂。处理方式：

1. 下载后降采样到 **32×32**（不要 16×16，糊成色块认不出）
2. 用最近邻插值放大到 48×48 显示
3. 主界面 48×48，HUD 条用 16×16（再降一档）
4. 缓存降采样后的结果，避免每次重算

## 八、对开发计划的影响

| 变化 | 影响 |
|---|---|
| 删除 P3 歌词系统 | **-4~5 人日** |
| UI 改原版像素风 | 省掉 ModernUI 依赖和自定义贴图，**-1~2 人日** |
| 主界面信息精简 | 省掉布局调试时间，**-1 人日** |
| 新增方块形态（若选 D） | **+3~4 人日** |

净变化：**约 -4 人日**（不含 D 的方块）。总工期从 25–34 人日降到 **21–29 人日**。
