# 技术栈方案 · 手持音乐播放器

> 版本 v1 · 2026-11-12
> 前提：MC 26.3 / Fabric / Java 25 / 无歌词 / 原版像素风 UI / 纯客户端模组

---

## 一、先定位真正的岔路口

所有人都在讨论"用 JLayer 还是 mp3spi"，但那不是重点。真正决定项目形态的是：

> **那个 OpenAL source，由谁来创建、谁来持有？**

MC 的音频链路是 `SoundInstance → SoundEngine → ChannelHandle(source) → OpenAL`。你插进去的位置不同，能力上限就完全不同：

| 插入位置 | 谁持有 source | 你能控制什么 | 不能控制什么 |
|---|---|---|---|
| 实现 `AudioStream` 交给原版 | 原版 | 音量、音高、attenuation（距离衰减） | 拿不到 source 句柄，**挂不了滤镜** |
| 实现 `AudioStream` + Mixin 取句柄 | 原版（你借用） | 上面全部 + **低通、遮挡、自定义衰减曲线** | 多声道、HRTF |
| 自己建 source | 你自己 | 全部，含多声道 / HRTF / 自定义空间模型 | 要自己处理 context 线程、设备切换、生命周期 |

三条路对应三种方案。第四条是"绕开 OpenAL"，单独算一类。

## 二、四套方案

### 方案一 · 纯原版管线

**技术组成**

| 层 | 选型 |
|---|---|
| 播放接入 | 实现 `net.minecraft.client.sounds.AudioStream` + `AbstractTickableSoundInstance` |
| 解码 | mp3spi 1.9.5.4 + jlayer 1.0.1.4 + tritonus-share + jflac |
| 网络 | JDK `HttpClient` + 自实现 eapi 加密 + Range 分段拉流 |
| 结构 | 单模块 Fabric，client-only，无 Mixin |
| 打包 | jar-in-jar + 包名 relocate |

**能力**：3D 定位 ✅、距离衰减 ✅、游戏音量联动 ✅、暂停/切场景自动回收 ✅
**做不到**：隔墙变闷、多声道、自定义衰减曲线

**成本**：24–31 人日（含方块形态）
**风险**：低。Net Music 用这套跑了三年、300 万下载，路径已被验证。
**适合**：想先把东西做出来，空间感只要"走远变小"就够。

---

### 方案二 · 原版管线 + Mixin 挂滤镜（甜点）

**技术组成**

| 层 | 选型 |
|---|---|
| 播放接入 | 同方案一（`AudioStream` + `SoundInstance`） |
| **增强** | Accessor Mixin 取 `SoundEngine.instanceToChannel` → `ChannelHandle.source`，对 source 挂 `AL_DIRECT_FILTER`（低通） |
| 遮挡 | 每 5 tick 从玩家到声源打一条射线，被方块挡住就压低低通截止频率 |
| 解码 / 网络 / 结构 | 同方案一 |

**关键约束**：AL 调用必须在 sound engine 线程执行。做法是把 AL 命令塞进 `SoundEngine` 的 executor 队列，不能在渲染线程直接调。

**能力**：方案一全部 + **隔墙变闷** + 可自定义衰减曲线
**做不到**：多声道、HRTF

**成本**：26–34 人日
**风险**：中。Mixin 点依赖 `SoundEngine` 内部字段名，mojmap 下要自己核对；1.21.6+ 音频引擎重构过，需在 P0 实测。
**适合**：想要"空间感"这个卖点，但不想承担自管 OpenAL 的风险。**推荐这条。**

---

### 方案三 · 全自管 OpenAL

**技术组成**

| 层 | 选型 |
|---|---|
| 播放接入 | 自建 ALC context（或复用 MC 的）+ 4 个循环 buffer 流式播放 |
| 解码 | JLayer 单库 + 自写 PCM 环形缓冲 |
| 空间 | `AL_POSITION` / `AL_ROLLOFF_FACTOR` / `AL_MAX_DISTANCE` / `AL_DIRECT_FILTER` |
| 高级 | `EXTFloat32` + `EXTMCFormats` + `SOFTDirectChannelsRemix` → 多声道 / 环绕 |
| 网络 / 结构 | 同方案一 |

**能力**：全部。可做多声道、可做自定义空间模型、甚至 HRTF（如果 OpenAL Soft 的 `ALC_HRTF_SOFT` 可用）
**代价**：自己管 context 线程、设备热插拔、音量分类、资源释放；与 MC 音频设备的抢占要处理

**成本**：36–46 人日
**风险**：高。这是 Music HUD 走的路线，它有 18 star 但版本停在 1.21.8，说明这条路维护成本不低。
**适合**：明确要做环绕声 / 多声源定位（比如服务器里摆一排音箱）。

---

### 方案四 · Java Sound 直出（对照组）

**技术组成**：`javax.sound.sampled.SourceDataLine` 直接输出到系统音频设备，完全不碰 OpenAL。

**能力**：能播、能暂停、能调音量
**做不到**：**没有任何空间化**、不受游戏音量控制、和 MC 音频设备切换容易冲突

**成本**：17–21 人日
**风险**：最低
**适合**：只想要"游戏里能放歌"，不在乎空间感。Dango Music 就是这么做的——它 624 star 靠的是 UI 和歌词，不是音频。

⚠️ **和你的需求冲突**：你明确要"手持发声器的空间感"，这条路给不了。

## 三、横向选型（四套方案共用的子决策）

### 3.1 解码

| 选项 | 覆盖格式 | 体积 | 建议 |
|---|---|---|---|
| mp3spi + jlayer + tritonus + jflac | mp3 / flac / aac | 约 1.2 MB | **推荐**，Net Music 同款 |
| 单 jlayer | 仅 mp3 | 约 300 KB | 够用，但以后加 flac 要返工 |
| 单 jlayer + jflac | mp3 / flac | 约 700 KB | 折中 |

**都要做包名 relocate**，否则和装了 Net Music 的整合包冲突。

### 3.2 网络层

| 选项 | 说明 | 建议 |
|---|---|---|
| JDK `HttpClient` + 自写 eapi/weapi | 零依赖，约 300 行加密代码 | **推荐** |
| 引第三方 Java 版网易云 API 库 | 省事，但多数已停更、依赖链脏 | 不推荐 |
| 打包本地服务进程 | 违反"只要模组本体" | 排除 |

### 3.3 工程结构

| 选项 | 说明 | 建议 |
|---|---|---|
| 单模块 `src/main` | 最快跑通，改起来直接 | **MVP 用这个** |
| `common` + `fabric` + `neoforge` | 为移植留口 | 等 v1 稳定后再拆 |
| Architectury | 抽象层，但 26.x 支持滞后 | 暂不考虑 |

### 3.4 物品 / 方块

| 形态 | 是否需要服务端 | 说明 |
|---|---|---|
| 仅手持物品 | 否，纯客户端 | 最简单，但声源只能跟着玩家 |
| 手持 + 可落地方块 | **是**，要 BlockEntity + 状态广播 | 空间音效的载体，多 3–4 人日 |

## 五、推荐：方案二，但按方案一的结构起步

具体做法是**先写接口，再填实现**：

```java
public interface AudioSink {
    void play(TrackSource src, SourcePos pos);
    void pause();
    void seek(long ms);
    void setLowpass(float cutoffHz);   // 方案一里是空实现
}
```

- 第一版填 `VanillaAudioSink`（方案一），三天内能出声
- 空间感增强时换成 `FilteredAudioSink`（方案二），只改一个类
- 万一以后真要做环绕声，再加 `OpenAlSink`（方案三），上层不动

这样做的价值：**你不会因为一开始选错而重写整个音频层**。方案一和方案三的差异，全部收敛在这一个接口后面。

## 六、对 PLAN.md 的影响

现有 `PLAN.md` 的 3.3 音频层就是方案一，P0.6 已经包含低通验证，实际等于"方案一打底 + 方案二预留"。

需要补的两件事：

1. 加一个 `AudioSink` 抽象层（约 0.5 人日，但省掉未来重写）
2. P0 增加一项：**验证能否通过 Mixin 拿到 `ChannelHandle.source`**——这是方案二成立的前提，也是最不确定的一环，必须最早验
